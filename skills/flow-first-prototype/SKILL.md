# Flow-First Prototype（流程优先原型）

## 目标

把“要哪些功能”改写成“谁在什么情境下，要完成什么任务，完成后发生什么”。原型是这条体验的可演示投影，不是功能目录的视觉化版本。

工作单位是**场景中的任务**，而不是页面或数据库对象。每个重要任务都要有：触发、已有状态、用户决策或动作、系统反馈、成功结果、失败或中断后的去向，以及需要时的角色交接。

## 先选择执行深度

根据范围和风险选择最小足够模式，不要让简单需求变成文档项目：

- **L1 单步/单角色**：低风险、单屏或单一动作。完成需求卡、一个 Job Story、一个 Screen Contract 和适用状态检查。
- **L2 跨屏/多步骤**：有多个动作、回访、搜索、编辑或角色交接。执行阶段 0–5，做一条主流程和追踪矩阵。
- **L3 高风险/复杂协作**：涉及审批、金额、权限、配置期与运行期、外部系统、多租户、审计或批量操作。在 L2 基础上使用 B 端清单、异常/恢复/并发检查和完整验收记录。

用户要求“快”时压缩篇幅，不删除与当前模式相应的判断。用户只要方向或信息架构时，停在流程和屏幕地图，不擅自生成代码。

## 不可妥协的判断

1. **结果先于功能。** 先写用户要改变的现实结果，再决定是否需要某个功能或页面。
2. **场景先于屏幕。** 屏幕必须服务于进入、理解、决策、操作、确认、交接或回访中的一个具体需要；不是每个实体都值得有一个菜单项。
3. **主路径先于边角。** 先确定一条最高价值的端到端主故事，再补会改变设计的异常、权限、恢复和批量场景。
4. **流程是连续的。** 上一步的输入、对象状态和用户心理预期要能解释下一步；提交之后谁接手、如何知道、看到什么，必须明确。
5. **范围可追踪。** 每个页面、动作和菜单项都要能追溯到一条故事或必要的系统约束；没有来源的功能进入“待验证/以后”清单。
6. **事实、假设、待确认分开。** 缺信息时登记假设并继续推进；只有会改变主路径、权限或数据模型的问题才阻塞工作。
7. **角色数量按事实决定。** B 端通常有多角色接力，但单角色流程可以成立；不要为了满足模板凭空制造角色。
8. **每个交互面只有一个主任务。** 屏幕、抽屉、弹层或内联区域都要有一个主 CTA、清楚的当前上下文和可见的下一步。
9. **不静默改写用户范围。** 用户明确点名的能力先保留在范围账本；若放到 Later 或 Out-of-scope，必须写业务理由、风险和验证人。

### 最小任务闭环契约

为每条 P0/P1 故事分配一个 `task_id`，贯穿故事、流程节点、状态迁移、交互面和回读案例。至少记录：

`触发 → 当前上下文/对象状态 → 一项主任务 → 即时反馈 → 成功证据 → 交接/通知/截止时间（适用时） → 失败、退出与恢复`

任何页面或动作无法挂到这条契约，就先进入停车场；系统自动动作可以没有交互面，但必须有可观察结果。

## 开始时先解码用户输入

- 用户只给出“做一个列表页/详情页”：先把它放回某条任务流程，确认入口、来时状态、主要决策和离开后的去向。
- 用户给出一串功能名：先建立 Must / Should / Later / Out-of-scope 范围账本；挂不上故事或系统约束的项目暂不进入 UI。
- 用户信息不足：最多先问 3 个会改变主路径的问题，每个问题说明它会改变哪条路径、权限、状态或集成；其他内容记入 assumptions（来源、置信度、影响、如何验证），用可回滚的假设继续。
- 每轮中间产物按“已知 / 假设 / 待确认 / 下一步”组织，避免把尚未验证的页面当成最终方案。

## 工作流

以下阶段可以在聊天中输出，也可以在项目里保存为对应文档。不要为了形式创建空文件；只有实际需要的产物才落盘。

### 阶段 0 · 需求解码与目标对齐

把用户的功能名改写成一张需求卡：

| 项目 | 要回答的问题 |
|---|---|
| 目标用户 | 谁在什么环境、设备和频率下使用？主用户是谁？谁受影响或接手？ |
| 触发与已有状态 | 什么事件让他现在必须处理？他已经知道或拥有了什么？ |
| 任务与结果 | 他要做出的关键决策/动作是什么？完成后现实中改变了什么？ |
| 当前替代 | 现在如何完成？哪里慢、容易错或无法追踪？ |
| 约束 | 权限、组织、数据、设备、合规、外部系统、SLA、并发等 |
| 成功信号 | 用户和业务如何知道做成了？能观察到什么证据？ |
| 非目标 | 这次明确不解决什么，避免范围膨胀 |
| 假设与待确认 | 哪些是事实，哪些是推断；哪些答案会改变方案 |
| 术语拆解 | “打款/发票管理/通知”等宽泛词，分别是记录、发起、校验、归档还是提醒？ |

同时列出首次使用、重复使用和异常情况下的关键情境。建立范围账本：Must、Should、Later、Out-of-scope，并为后两类写业务原因、风险和验证人。对金额、审批、支付、身份、隐私或不可逆操作，额外登记业务规则、幂等、职责分离、敏感字段和审计要求（适用时）。

**门禁 0：** 能用一句话说清“谁在什么情境下，为了什么结果而行动”，并区分了必须解决、以后再做和不在范围内的内容。不能只复述功能名。未知项可以保留，但必须有假设、置信度和验证方式。

### 阶段 1 · Job Story 与优先级

用下面的格式写主故事和必要的次要故事：

\`\`\`text
当 <具体情境、触发时机和已有状态>，
我想 <要做的决策或动作>，
以便 <可观察、可验证的结果>。
\`\`\`

每条故事补充：`task_id`、主角色、前一个动作、完成后的下一位接手者、使用频率、影响/风险、成功证据、验收条件、SLA（如适用）和优先级（P0 主路径 / P1 高频或高风险分支 / P2 增强项）。故事描述动机和结果，纯粹的“点按钮、保存数据”移到任务步骤或实现清单。

把故事排成 story map：用户旅程阶段 → 用户步骤 → 系统响应 → 成功/失败证据。先只保留一条 P0 主故事，形成能端到端达成结果的 MVP 薄切片；其余放入后续版本或停车场。

**门禁 1：** 每个 P0/P1 需求都能回答“解决谁的什么问题、如何知道做成了”；每个计划中的页面、动作和功能都有故事或约束来源。无来源的项目不能悄悄进入原型。

### 阶段 2 · 端到端流程与系统模型

为 P0 主故事画一张端到端流程。流程可以用 Mermaid，也可以用表格；多角色时使用泳道，只有一个角色时仍要明确系统和外部系统的响应。每一步至少写清：

- 入口、前置条件、用户看到的上下文
- 用户动作或决策、系统响应、对象状态迁移
- 成功结果、下一步和交接契约（接收人、通知渠道、上下文、期限、代办/升级、能否退回）
- 校验失败、业务拒绝、无权限、网络/外部依赖失败、并发冲突
- 等待、超时、撤回、放弃、草稿、恢复和重新进入
- 正常完成、被接管、转交和可追溯的退出口

把导航/信息架构从用户任务、待办和使用频率推导出来。高频主任务、待处理事项、搜索和回访入口优先；配置、报表和低频管理能力按角色与风险分层，不要把所有对象名平铺成左侧菜单。跨流程入口和直接深链也要标出来。

只补对当前产品有真实影响的分支。若流程确实是直线，写出原因；不要凭空制造角色或异常。

**门禁 2：** 每条 P0 故事都有从入口到成功或可解释失败的路径；关键异常和恢复路径已覆盖；流程中的人、系统、外部依赖和状态变化没有“提交后自动完成”的黑箱。

### 阶段 3 · 屏幕地图、交互契约与状态矩阵

从流程推导交互面，不从功能列表倒推。一个流程节点可以落在页面、抽屉、弹层、向导步骤或内联动作中；按任务连续性合并，避免每个节点都变成新页面。每个交互面记录：

| 屏幕/区域 | task_id / 目的 | 谁能进 | 入口与来时状态 | 用户要作的主要决策 | 主动作 | 系统反馈/对象变化 | 下一步与返回 |
|---|---|---|---|---|---|---|---|

每个会影响任务的组件至少考虑适用的状态：首次/回访、正常、加载/超时、空（从未有数据 vs 筛选后为空）、字段校验、业务规则失败、网络/外部系统失败、无权限（入口隐藏/可见但禁用/操作后拒绝）、只读/归档、未保存/过期、并发冲突、部分成功。标记 N/A 并说明原因，不要机械地给不适用的屏幕制造状态。每个异常都写下一步和数据是否保留。列表同时检查 0、1、20、2000 条、长文本、异常值和批量部分成功。

建立可追溯矩阵：`Story → Flow node → State transition → Screen/action → Expected result → Review case`。双向检查：不能有无法演示的主流程节点，也不能有没有故事来源的孤儿屏幕或孤儿动作。

**门禁 3：** 每个交互面都能说明它为哪一步减少了什么认知或操作负担；主故事的入口、动作、反馈、回访和异常都能从屏幕地图找到；状态和权限与对象状态机一致。

### 阶段 4 · 生成整条可评审原型

只有在阶段 3 通过后才写界面代码。一次生成一条完整流程，让交互面之间真跳转、真传参、真共享状态。实现约定见 [`references/prototype-conventions.md`](references/prototype-conventions.md)。

原型默认中保真，先验证任务和信息层级。必须能：

- 从每个定义的入口进入，包括待办/通知/列表和直接 URL（若适用）
- 完成 P0 主故事，看到成功反馈、下一位接手和回访结果
- 按模式和适用性切换角色、状态和数据规模，检查权限、空态、错误、恢复和边界数据
- 在列表、详情、编辑、确认等交互面之间使用同一份 mock 状态

若用户只要方案，不要为了“完整”擅自生成 HTML；输出屏幕地图和关键交互契约即可。

**门禁 4：** 共享状态、路由/事件和主故事可穿通；对象状态、权限和界面动作没有矛盾；每条 P0 故事至少有一条可重复的演示路径。

### 阶段 5 · 场景回读与质量验收

拿着每条 P0/P1 故事做真实任务回读，而不是只检查页面是否存在：从触发开始走到成功、驳回/失败、恢复和交接，记录卡点、歧义、丢失的上下文和不一致的状态。

用 0/1 检查以下项目：

- 用户结果、主路径、MVP 薄切片和范围清楚
- 故事、流程、状态、交互面和验收案例可双向追踪
- 角色交接、通知、期限、代办和审计可见（适用时）
- 成功、拒绝、异常、中断、恢复和并发路径可解释
- 入口、返回、深链、搜索和跨流程跳转可用（适用时）
- 页面状态、权限、数据规模和批量部分成功已覆盖（适用时）
- 关键动作有明确反馈，失败告诉用户下一步
- 原型使用共享数据，术语、状态和对象在各交互面一致

未通过项按类型处理：流程/状态/权限问题回到阶段 2–3；信息层级、交互或文案问题在阶段 4 修正；视觉润色最后处理。验收记录、未决问题和关键取舍（选择了什么、放弃了什么、为什么）应保留，方便下一轮继续。

## 反模式

看到以下情况暂停生成更多页面并回到相应阶段：

| 症状 | 应回到哪里 |
|---|---|
| 用户说“做个 XX 页”就开始写 HTML | 阶段 0：确认它属于哪条任务流程 |
| 左侧菜单是用户管理、订单管理、日志管理等名词堆 | 阶段 1–2：按任务、频率和待办重做信息架构 |
| 故事写成“我想保存，以便保存成功” | 阶段 1：重写真实动机和可验证结果 |
| 只有万能管理员，没有实际接手人 | 阶段 0–2：按责任、权限和交接拆角色 |
| 只有 happy path，提交后“系统自动完成” | 阶段 2：补系统泳道、等待、通知和异常 |
| 屏幕逐张生成，假数据和状态对不上 | 阶段 3–4：建立追溯矩阵和共享 mock 状态 |
| 每屏只有正常态，或把所有状态机械套在每屏 | 阶段 3：按风险补适用状态并说明 N/A |
| 有“提交”但不知道谁看到、在哪看到、何时处理 | 阶段 2：补交接契约 |
| 功能没有故事来源，或故事没有可演示路径 | 阶段 1–3：删除孤儿功能或补齐流程 |
| 错误只显示“失败”，没有恢复动作或数据保留说明 | 阶段 2–3：定义错误类别和下一步 |
| 配置页和运行期使用页各自成套，改配置影响不到进行中的数据 | 阶段 0–2：建配置期/运行期关系和版本规则 |
